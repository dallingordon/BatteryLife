--- Zn-ion regression gap: root-cause analysis (no GPU needed) ---
Checked cycle_length_stats.csv (9/8 audit) for per-source eol distribution stats:
  ZN-coin  n=121  mean=332.6  std=379.3  cv=1.14  min=12   median=168   max=1621
  CALB     n=27   mean=878.9  std=496.9  cv=0.57  min=104  median=1171  max=1411
  NA-ion   n=34   mean=180.5  std=52.6   cv=0.29  min=102  median=177   max=307

cv (std/mean) tracks the regression-reproduction gap almost perfectly: ZN-coin (most skewed,
cv=1.14) had the worst regression mismatch vs published (MAPE ~0.9-1.3 vs 0.558); NA-ion (least
skewed, cv=0.29) had the smallest mismatch (0.32 vs 0.27); CALB (cv=0.57) reproduced cleanly.

Checked data_loader.py / run_main.py: regression's MSE loss trains on labels passed through a
per-dataset StandardScaler (mean/std) fit on that dataset's own unique_labels. geo_bins NEVER
uses that scaler for its target - it converts back to raw value (labels*std+mean_value) and
bins against one FIXED GLOBAL range [1, 3842] with log-spaced edges (see utils/geo_bins.py) -
structurally immune to a bad per-dataset scaler fit. A StandardScaler fit on Zn-ion's skewed
121-cell distribution (a few huge-life outliers vs a low median) is a poor normalizer, and MSE
regression's gradient is known to be outlier-dominated - exactly the mechanism already floated
as a working hypothesis in the 9/8 notes ("cycle-life labels are heavily right-skewed... MSE's
squared-error gradient is dominated by the long-tail... geo_bins naturally more robust").

Conclusion: Zn-ion's regression re-run is probably NOT a reproduction bug - it's exposing a
real weakness of vanilla MSE regression on a skewed small dataset, which is the actual
mechanism behind geo_bins' advantage. Reframes the earlier "fix the regression baseline" framing
- deprioritized the accumulation_steps batch-size test (train_eval_scripts/
CPMLP_znion_accumtest_qsub.sh, CPTransformer_znion_accumtest_qsub.sh - written but not yet run,
kept as a cheap rule-out if we want to be thorough) since it targets the wrong mechanism.

Possible cheap confirmation (no new full training needed): try log-transforming the label before
StandardScaler.fit instead of raw eol, see if that alone closes the regression gap on Zn-ion.
Also: redo this same cv check for MATR/Li-ion once the missing-pkl issue is fixed, to see if cv
predicts that gap too - would make this a 3-for-3 pattern instead of 2-for-2.

  Stanford_2.zip - same failure mode (not used by any of CALB/Li-ion/Zn-ion/Na-ion though, so

Fix: re-run unzip with UNZIP_DISABLE_ZIPBOMB_DETECTION=TRUE (documented Info-ZIP escape hatch,
safe here since this is a legit large Zenodo scientific archive, not an untrusted file):

--- Reproduction quality summary: Na-ion good, Zn-ion bad (neither is a data bug) ---
Na-ion regression reproduces well: CPTransformer 0.280 vs published 0.255 MAPE (~10% relative,
within the paper's own std). CPMLP 0.321 vs published 0.274 (~17% relative, a real but modest
miss). Normal reproduction variance, nothing alarming.

Zn-ion regression does NOT reproduce well: CPMLP 1.037 vs published 0.558 (~86% relative miss,
roughly double). CPTransformer 0.663 vs published 0.515 (~29% worse). Ruled out (see above)
both a dataset-dispatch bug and a hyperparameter mismatch - printed args confirm 'dataset':
'ZN-coin' and exact table hyperparams (batch correctly doubled) were used. So this is NOT a
Li-ion-style data/extraction bug. Pattern is consistent with the skew hypothesis at the level of
"Zn-ion is the hardest chemistry" (published MAPE is already the worst of the four, cv=1.14 is
the highest), BUT skew alone does NOT explain why OUR reproduction is worse than THEIRS on the
identical method - they dealt with the same skewed labels and got 0.558. Real remaining
candidates for the reproduction-specific gap (none confirmed yet):
  - single-GPU batch-doubling vs their 2-GPU DDP introducing a small but real optimization
    difference that gets amplified because Zn-ion's regression loss is already fragile (skewed,
    small-n) - geo_bins doesn't show the same gap because its loss is bounded/more robust to the
    same perturbation
  - seed/hardware nondeterminism (same seed value != same random draws across different
    GPU/CUDA/PyTorch versions), again more visible on an already-fragile optimization
  - unverified protocol details (train_epochs/patience/model-selection criterion vs whatever the
    paper actually used) - not yet checked against a paper source
