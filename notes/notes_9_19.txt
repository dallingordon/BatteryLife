--- IDEA (parked, not implemented): per-chemistry loss weighting for pooled training ---
Pooled training is ~84% Li-ion by cells (train cells: Li-ion 515, CALB 17, Zn-ion 60, Na-ion 20 = 612).
Idea: scale the loss per chemistry so the big chemistry doesn't dominate - weight each sample in chemistry c
by N_c^(-alpha), then rescale so the mean weight over the training set is 1 (keeps loss scale / effective lr
comparable to unweighted runs). Flag shape: --chem_loss_alpha (float, default 0 = off), not a boolean.
  alpha=1   -> chemistries contribute equally to the loss
  alpha=0.5 -> softer, sqrt balancing
Approx weights (cell counts as proxy): alpha=1: Li-ion ~0.3, CALB ~9, Zn ~2.5, Na ~7.7
                                       alpha=0.5: Li-ion ~0.7, CALB ~3.8, Zn ~2.0, Na ~3.5
Why attractive:
  - model selection already averages per-chemistry val MAPE with equal weight, so this aligns the training
    objective with the selection criterion
  - in regression it may help Zn-ion (small labels -> small errors under the Li-ion-dominated pooled scaler)
Risk: at alpha=1 CALB's 17 cells get ~9x weight; each cell gives ~100 near-duplicate truncated samples, so
the model may memorize those 17 cells. Would sweep alpha in {0, 0.5, 1}, CPMLP first.
Implementation sketch (when/if wanted): the training loss is already mean(loss * weights) for both regression
and geo_bins, so fill the per-sample `weights` in Dataset_pooled (train flag only) from chemistry_counts();
no model or training-loop change. Existing --weighted_loss is a different thing (KDE over labels).
Alternative: oversample small chemistries with a weighted sampler (equivalent in expectation, noisier, more plumbing).
Orthogonal to --chem_fusion (can combine).
Status: dgordon pondering.

DESIGN (as agreed)
- Same pooled train cells + chemistry id + same exclusions (no label, no pkl, eol <= 100).
- Prefixes 1..min(stored cycles, eol-1) per cell (not capped at 100).
- --full_max_cycles N      longest prefix used. empty = no max.
- --full_prefixes_per_cell K   at most K random prefixes per cell per epoch, redrawn each epoch (seeded by seed+epoch),
                            chemistry-agnostic. empty = drop nothing. Cells with < K prefixes contribute all.
- Batch size 1, NO padding. Batch layout = pooled 8-tuple (curves [1,L,3,300], mask [1,L] all ones, labels, life_class,
  scaled_life_class, weights, seen_unseen, chemistry_ids). Assert in collate if batch > 1.
- Call data_set.set_epoch(e) before iterating each epoch (prints per-chemistry samples / cycle-steps / shares).
- Val/test unchanged: existing per-chemistry Dataset_pooled loaders, prefixes 1..100, published cells.
- Cache = <root_path>/full_cycle_cache/<cell>.npy ([n_cycles,3,300] float32, cycles 1..eol-1) + <cell>.meta.json.
  max_cycles applied at load time, so changing it never needs a rebuild. Loader errors with the exact command if cache missing.
- Curves use the baseline's own get_charge_discharge_curves, one cycle at a time (same per-cycle code, O(N) not O(N^2)).
- Unusable cycle (exception / NaN / no rows): cache for that cell STOPS before it, recorded in meta
  (truncated_at_cycle, reason); precompute prints these at the end. Worth a look once it finishes.
- label scaler is fit on the included cells' eol, i.e. the same cells Dataset_pooled(train) fits on. Hand it to val/test loaders.

--- SCC reaper kills: CUDA_VISIBLE_DEVICES bug, stage 1 resubmitted (9/22 evening) ---
Cause of the repeated "terminated because it was using gpu 0, which was not assigned to its batch job" emails:
every *_qsub.sh script launched with `CUDA_VISIBLE_DEVICES=0 accelerate launch ...`. SGE sets CUDA_VISIBLE_DEVICES
to the GPU it actually assigns; the hardcoded =0 overrode that and pinned us to physical GPU 0. Jobs that happened
to be assigned GPU 0 ran fine, everything else got killed by the reaper. Because the reaper kills the python
process, not the batch job, the seed loop just moved on to the next seed, which got killed too -- so jobs "finished"
with no results.

Fix (commit "qsub scripts: stop overriding scheduler's CUDA_VISIBLE_DEVICES", pulled on SCC): removed the
CUDA_VISIBLE_DEVICES=0 prefix from all 22 train_eval_scripts/*_qsub.sh. Inside a job the assigned GPU still shows up
as cuda:0, so nothing else needed to change. The older non-qsub scripts (CPMLP.sh etc., CUDA_VISIBLE_DEVICES=0,1)
were left alone -- they're from the original multi-GPU-box repo; don't qsub them as-is.
Note: SGE spools the script at qsub time, so queued jobs keep the old script -- they had to be qdel'd and resubmitted.
